#### MCP server

18 commands shipped on the `golmet` binary:

- `golmet validate` — end-to-end workspace validation against FORMATO v1 (H1–H10 / S1–S5) with parseable evidence, `--json` structured output, and `--tolerant`/`--strict` modes; non-zero exit blocks CI.
- `golmet init` — scaffolds a product workspace or organization container (`.golmet/` kit zone, `golmet.yaml`, engine adapters for `.opencode/`, `.mcp.json`, `.cursor/`).
- `golmet install` — onboarding wizard covering 7 agent engines and a catalog of 12 MCP servers, with already-registered badges and cascaded post-install verification.
- `golmet update` — refreshes the vendored BASE skill subset via `go:embed` with a SHA-256 manifest; `--full` materializes the FULL workflow into the engine config (embedded or external core).
- `golmet status` — workspace dashboard summarizing artifacts, states, and staleness.
- `golmet next` — deterministic recommendation of the next action, prioritized `p1..p9`.
- `golmet doctor` — environment health checks (9 checks) with remediation hints; runs a Jev smoke test by default (`--no-network` skips it).
- `golmet adopt` — FORMATO adoption handshake for existing workspaces: classified dry-run first, then deterministic apply, preserving legacy layouts.
- `golmet eval` — deterministic eval checker (15 checks) over a fixture suite, with JSON output for CI; every evaluated fixture also gets a markdown report in `~/.golmet/eval-reports/` (kit machine state, 50-report retention), with the path printed as `relatório: <path>`.
- `golmet tools` — installs supporting tooling (e.g. `tools install codegraph`) with supply-chain verification (SHA-256 checksums + attestation).
- `golmet mcp` - stdio MCP server exposing 13 tools (see below).
- `golmet index` — rebuilds `golmet.index.json` (the kit-written state index) after merges or corruption.
- `golmet pack` — manages L2 content packs: `pack add`, `pack update` (sync + overlay, engine required), `pack publish` (state packs: commit WIP + push to origin), and `pack list` (shows the `kind` of each pack). Packs come in two archetypes: `overlay` (default — read-only cache, `provides` in `agents/`/`skills/`) and `state` (bidirectional Git working copy at `<config>/packs/<id>`: skills/agents materialize by overlay while `knowledge/`, `accumulation/` and `rules/` live in the clone; `update` auto-commits local accumulation before rebasing and never discards it).
- `golmet db` - database layer commands; `db drift` deterministically compares `DATA_MODEL.md` entities against the EF Core `ModelSnapshot` (migrations drift for the `gm-dba` layer).
- `golmet lint` - deterministic structural sweep (read-only) over the kit/config/packs: dead references (L1), orphans (L3), stale content-manifest entries (L4), non-canonical names (L5), ghost `gm-*` components not in the registry (L6 - error in sources, warning in historical docs), canonical folder structure (L7 - the canonical tree is declared in code and documented in FORMATO §9.1, which also lists the declared anti-false-positive heuristics and allowlists) and definitivo↔template structural conformance (L8 - the config's AGENTS.md/profiles keep the minimal declared skeleton of their kit templates; extra sections are legitimate evolution, only structural LOSS flags). Findings carry severity, file (+line) and a PT-BR remediation; exit 0 clean, 2 with findings; `--json` for CI/agents. The CI runs it against the kit repo itself.
- `golmet template <agents|client-profile|operator-profile>` - emits the kit template straight from the embed (`--out <path>` writes to a file). **Templates are construction artifacts: they live in the kit and are NOT installed** — the materializer skips them (`nonDepositTemplates`) and removes stale provenance from the content manifest; the config carries only the definitives. This is the official path for `gm-setup` to obtain a skeleton during repair.
- `golmet uninstall` - removes the global Golmet structure from the machine, layer by layer, with dynamic discovery from the content manifest + personal.json + engine config: (1) materialized tooling (managed layer-core files), (2) kit state (`<config>/.golmet/`), (3) installed packs (local working copies - **DESELECTED by default**; deleting a pack removes ONLY the local working copy, the remote repo is deleted manually on GitHub), (4) personal-by-design data from personal.json (opencode.jsonc excluded - it belongs to the engine), (5) unmanaged files (e.g. plugins/), (6) engine registry (removes ONLY the Golmet entries from `opencode.jsonc` - MCP golmet + gm-dev-* permission overrides; surgical JSONC edit, idempotent, validated before writing, the file and the rest of the engine config remain). Interactive wizard with per-layer counts (defaults as above) + final confirmation with the pack warning; `--only <csv> --yes` for non-interactive, `--dry-run` to list without deleting, `--json`. Empty kit-created dirs are removed after deletion; never touches anything outside the config root + validated state-pack working copies.
- `AGENTS.template.md` is now kit-managed content: the versioned, organization-neutral template (IMP-105) lives in `coredata/templates/` and the FULL install materializes it into `<config>/AGENTS.template.md` as a core-layer managed file (previously a hand-maintained orphan describing the old model - 11 MCP tools, T1 under `knowledge/`, no router/writers). The template is synced with the current workflow (13 tools incl. `gm_lint`/`gm_upgrade`, knowledge-routing T1-T5 with the canonical writers `gm-nuance-collector`/`gm-rule-keeper`, the `gm-knowledge-route` router line, pack rules in-place in the lazy index, EN pattern-library types) and is covered by the lint (L1 scan; no longer orphan-allowlisted).

#### MCP server

- `golmet mcp` serves 13 tools over stdio: `gm_validate`, `gm_doctor`, `gm_next`, `gm_status`, `gm_index`, `gm_eval`, `gm_eval_reports`, `gm_jev_classify`, `gm_update`, `gm_pack_update`, `gm_pack_list`, `gm_upgrade`, and `gm_lint` - so agent engines drive the kit without shelling out.
- `golmet upgrade` - self-update of the binary from the latest GitHub release: semver comparison tolerant to the `v` prefix (`--check` is read-only and reports `{current, latest, has_update}`; local builds report `dev`), platform asset selection, mandatory SHA-256 validation against the release `checksums.txt` (missing/mismatched checksum aborts without touching the binary), Windows-safe replacement (current binary renamed to `<bin>.old` on the same volume, new one moved in place, `chmod 755` on unix), `HTTP(S)_PROXY` respected and `GITHUB_TOKEN`/`GH_TOKEN` used when present (never required). `gm_upgrade` MCP tool mirrors the flow (`check=true` read-only; applying requires `confirm=true`).
- Release automation: tag-push workflow (`.github/workflows/release.yml`) cross-compiles the binary for windows/amd64, linux/amd64, linux/arm64, darwin/amd64 and darwin/arm64 (ldflags inject the tag into `golmet -v`), generates `checksums.txt`, and publishes the GitHub Release with the matching CHANGELOG section as notes.
- State packs (pack archetype `kind: state`): a bidirectional Git working copy at `<engine-config>/packs/<id>` instead of a read-only cache. `skills/` and `agents/` materialize into the engine config via the same 3-way overlay (pack ownership replaces core-rendered files for the same path), `rules/packs/<id>.md` is copied as managed content, and `knowledge/`/`accumulation/` stay in the clone where domain readers point at. `golmet pack update` auto-commits uncommitted local accumulation (`sync:` commit) before `fetch` + `rebase` — a rebase conflict fails with remediation and never discards data; `golmet pack publish <source>` commits WIP (`publish:`) and pushes to origin (manual push by design). `pack add` on an existing working copy with a matching `origin` adopts it (operator migration path) instead of recloning. The doctor classifies state-pack working-copy files as safe (versioned in the pack's own repo), counting only uncommitted changes as risk. `requires-core` accepts only `>=X.Y` — ranges are rejected with an error citing the accepted format.
- Eval reports are kit machine state: the kit writes each eval's markdown report to `~/.golmet/eval-reports/` (same machine-state convention as `~/.golmet/packs` and `~/.golmet/sources`; 50 most-recent retention by mtime) — the workspace never receives reports. `gm_eval` exposes the absolute `report_path` in its payload, and the new `gm_eval_reports` tool lists the stored reports (newest first, capped at 50, with `skill`/`fixture` parsed from the filename) — the runtime never manages the folder: it runs `gm_eval` and reads the file via file tools when it wants the human report.
- Jev client integration (TypeSafe System One classification) via the `/v1/systemone` route with typed `state`+`model` payloads and question specs.

### Changed

- Install wizard profiles renamed with **contract semantics**: `essencial` (the repository kit — 16 `gm-*` skills in the workspace `.golmet/` zone, versioned with the repo, any agentic engine) and `completo` (the full experience on your machine — 93 components in the engine's format, installed in your global config). **`completo` requires an engine with native skills** (criterion: `SkillsDir != ""` — today only opencode and claude-code): the wizards filter the engine list when completo is chosen, and `install`, `update --full` and `gm_update` fail closed with the compatible list instead of silently degrading; the workspace-zone pipeline remains internal (lib-level). The wizard asks the profile **before** the engine (plain and VT); `base`/`full` remain accepted as internal flag aliases and the report always cites the canonical name. Layer names L0–L3 (DR-021) are unchanged.
- The legacy human-knowledge layer was renamed from `reverse/guia/` to English `reverse/guide/` (OVERVIEW.md, IMPACT_MAP.md, GUIDES/, FORMS/) — naming settled after the initial FORMATO draft.
- FULL-layer installation evolved from a plain embedded materialization into the three-way overlay (DR-021) with conflict preservation and provenance tracking, superseding the first L1 drop.
- Jev client transport reworked to the `/v1/systemone` route with corrected `state`+`model` payloads, replacing the initial client wiring.
- Install wizard improved with already-registered badges for vscode/cursor/gemini and cascaded post-verify, refining the initial onboarding flow.

### Fixed

- `install`/`update` no longer treat EOL differences (CRLF/CR on disk vs the kit's canonical LF — leftover from PowerShell edits/migrations) as local customization: all installed-vs-target comparisons normalize EOL, and an EOL-only difference is **silently cured** by rematerializing the file in LF, counted as written — no scary "modificadas localmente"/conflict warnings, and content manifests converge. Real content differences keep the exact DR-008 preservation behavior. Re-runs with byte-identical content are now true no-ops (0 written).

### Security

- Path safety on both source and destination: rendered paths validated against traversal (allowlist `agents/`/`skills/`), symlink/junction escape rejected with real containment via `EvalSymlinks`.
- Credential redaction: Git URLs are redacted in manifests, payloads, and error messages.
- Fail-closed Git cache: a dirty sync cache aborts before any `pull --ff-only` runs.
- MCP mutation safety: state-changing tools (`gm_update`, `gm_pack_update`) require `confirm=true`, and `dry_run` writes nothing to runtime, manifest, or cache.
- Pack compatibility gate: `requires-core` is validated against the kit version before a pack overlay applies.
